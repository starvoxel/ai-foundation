### Key Design Decisions

1. **Decision**: The three currently-`Approved` records (`AIF-PROC-001`, `-002`, `-006`) go through a real two-commit sequence — commit the reformatted record with `Status: Draft`, present it, wait for explicit human re-confirmation, then commit a second, separate change setting `Status: Approved`. They are never combined into one commit that silently flips the status field.
   **Rationale**: Epic §6 (Security Considerations): "setting `Status: Draft` temporarily must not silently skip back to `Approved` without a new, real human confirmation. This is a plan-lifecycle gate, not a formality, even though the underlying decision content is not changing, only its format." This mirrors `skill/plan-lifecycle`'s own commit-gate procedure exactly, applied to a decision record instead of a plan.
2. **Decision**: The Metadata table's `Author (Agent)` and `Approved By` fields are carried over unchanged from the original record (`Architect` and `Jeremy`/`Jeremy Smellie` respectively) — migration is a reformat performed by AI-Engineer, not a re-authorship. `Created` date is also carried over unchanged (original creation date, not migration date).
   **Rationale**: The Epic's migration-treatment text describes this as reformatting existing records to a new template shape, not producing new decisions; changing `Author (Agent)`/`Created` would misrepresent who made the original decision and when. This matches the precedent already visible in AIF-META-001's own Metadata table style (real original author/date preserved).
3. **Decision**: All five records move into `docs/decisions/process/` — Tier does not affect folder placement, only ID prefix pattern and template shape used. Domain (`process`) and folder are uncontested for all five, including AIF-007, whose own already-Draft content already self-identifies as Process domain.
   **Rationale**: Folder/ID-prefix is keyed by Domain per AIF-META-001's scheme (`{ProjectID}-{DomainCode}-{###}`), independent of Tier. AIF-007's Tier (B, resolved per Open Question 7) only determines which template shape (Tier A `decision-record` vs. Tier B `decision-brief`) its own content is reformatted into.
4. **Decision**: The grep-and-update step (Section 5, In Scope) explicitly excludes `AIF-META-001`'s own embedded "old ID" migration-table column and the Epic AIF-002's own migration table — both are historical mapping tables where the old-ID values are the documented *subject* of the table, not stale references to be replaced.
   **Rationale**: Blindly find-replacing `AIF-004` → `AIF-PROC-001` inside a table whose entire purpose is "here is what AIF-004 becomes" would corrupt the table's meaning. Per Open Question 8's resolution, any update to `AIF-META-001`'s own prose (a single pointer/reference edit, not a find-replace) is chunk AIF-002-015's scope, not this chunk's.
5. **Decision**: Forward-references to `AIF-006`→`AIF-PROC-003` and `AIF-008`→`AIF-ARCH-004` are written into this chunk's five records now, even though neither target file will exist until chunks AIF-002-010/AIF-002-011 land.
   **Rationale**: Epic §8's parallelization note states explicitly that every new ID is already fully determined by the migration table, so "no chunk needs to wait for another migration chunk's actual file to exist to write a correct cross-reference string." This is the same reasoning already applied by AIF-002-002 to justify chunks 010-013 all depending only on 002, not on each other.
