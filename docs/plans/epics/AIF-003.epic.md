## 2. Goal

`AIF-META-002` established that an `Approved` Decision Record currently has exactly one governed post-approval path — supersede the whole record — which is disproportionate for a typo, a stale ID reference, or a revision to one section whose reasoning still holds. This Epic builds the three-rung ladder that record defines: an ungated `## Errata` rung for changes that provably cannot alter the decision, a gated `## Amendments` rung (new `Amending` status, two-commit confirmation) for scoped changes where the original rationale still holds, and the existing `Superseded` rung for genuine reversal. It also repairs the half-wired `Supersedes` handling in `lib/decisions.js`, without which the index would misdescribe the very ladder it is being extended to represent.

After this Epic, a domain owner correcting one section of an approved record has a proportionate, auditable path that does not require re-approving content nobody disputes, and `docs/decisions/index.json` reports amendment state and supersede relationships accurately.

## 5. Feature Description

### User-Facing Behaviour

The "users" here are the agents that author and consume Decision Records, and the human who approves them.

**Rung 1 — Errata (ungated, anyone).** An author notices a typo, a dead path, or an ID that was renumbered elsewhere. They apply the fix, append a row to the record's `## Errata` table (`#`, `Date`, `Change`, `Author`), and commit once with an `Errata: ...` message. `Status` is untouched, `Last Amended` is untouched, no inline marker is added, no approval is sought, and the index is unaffected in substance. The rung is only available when the change *provably* leaves the rendered meaning of the decision unchanged — and doubt disqualifies (see Business Rules).

**Rung 2 — Amendment (gated, domain owner).** The domain owner needs to change what a section says, but the original rationale still holds. In one commit they: apply the body edit, add `*(amended — see Amendment N)*` at the point of change, append an `## Amendments` row with `Outcome: Pending`, and set `Status: Amending` (commit message `Propose amendment: ...`). They then present it to the human. On confirmation, a second commit sets `Outcome: Approved by {name}`, sets `Last Amended | {YYYY-MM-DD} (Amendment {N})`, and returns `Status: Approved` (`Amend decision: ...`). On rejection, the second commit reverts the body edit and the inline marker, sets `Outcome: Rejected by {name}` — the row stays — and returns `Status: Approved` (`Reject amendment: ...`). While the record sits at `Amending`, every existing approval gate treats it as not approved, so no new dependent work may start against it.

**Who makes the second commit.** For most domain owners this is unchanged from `skill/plan-lifecycle` Step 4 — the agent edits and commits after the human has decided. Architect is the exception: it may write `Status: Approved` into the file but must not commit that change, so the human makes the confirm/reject commit for Architecture-domain records. The gate is identical either way; only the hand on the commit differs.

**Rung 3 — Supersede (unchanged in procedure, repaired in tooling).** The original rationale no longer holds. The existing full Tier A cycle applies and the record moves to `Status: Superseded`. What changes here is that the relationship finally shows up in `docs/decisions/index.json` instead of being reported as two permanently empty arrays.

**Reading a record.** A reader can tell at a glance whether a record has ever been amended: the presence of `Last Amended` in the Metadata table is itself the signal, and the `## Amendments` table names the section, the change, the rationale, and the outcome. Recovering the exact pre-amendment wording still requires `git log` — an accepted trade-off in `AIF-META-002`, not an omission to be fixed here.

### Data Flow

1. An author edits a `.decision.md` file under `{paths.decisions}/{domain}/` and selects a rung.
2. The rung determines the commit sequence (one commit for errata; two for an amendment, with a human decision between them) and whether `Status` moves.
3. `aif index -d` (`lib/commands/index.js` → `lib/decisions.js`) re-reads every record: `parseMetadataTable` supplies `Status`, `Last Amended`, `References`, and (new) `Supersedes`; a new section-level parse counts `## Amendments` data rows.
4. `buildDecisionIndex` inverts `References` → `referenced_by` (unchanged) and `Supersedes` → `superseded_by` (new), and emits `last_amended`/`amendment_count` per entry. `## Errata` is read by nothing.
5. Consuming agents (per `steering/global/knowledge-consumption.md` and `skill/plan-lifecycle`) check the record's status positively for `Approved`. `Amending` fails that check with no new code path.

### Business Rules

- **The errata test is about meaning, not location.** A change qualifies as errata only if it provably leaves the rendered meaning of the record's substantive sections unchanged — `Options Explored`, `Decision`, `Design`, and `Impact on Planning` at Tier A; `Rationale`, `Decision`, and `Impact` at Tier B (a brief has no options section by construction, so `Rationale` occupies that slot). A typo inside `Decision` is errata; a clarifying rewrite of an option's stated weakness in `Options Explored`, or of the reasoning in `Rationale`, is not.
- **Doubt disqualifies.** If it is not obvious that a change leaves meaning unchanged, it is not errata. This default-deny tie-breaker is what makes an ungated rung safe, and it must appear in the agent-facing wording, not just here.
- **`Status`, `Tier`, and `Domain` changes are never errata.** Other metadata corrections may be.
- **Amendments never carry their own Decision ID.** If a change feels like it needs one, that is the signal to supersede instead.
- **Authorship follows `AIF-META-001`.** Errata: anyone. Amendments and supersedes: the domain owner. The errata test therefore gates authorship as well as approval.
- **Both new sections are append-only.** A row's `Outcome` is filled in once when the cycle closes; rows are never edited afterward and never deleted. Rejected amendments stay in the table.
- **`Last Amended` is optional and forward-looking.** It must not be added to `REQUIRED_FIELDS` in `lib/decisions.js`. Errata never touch it.
- **`Amending` blocks all dependent work**, regardless of which section is being amended, and regardless of whether that section relates to the dependent work.
- **No gate anywhere special-cases `Amending`.** Every gate checks positively for `Approved`; adding a special case would violate `reference/status-vocabulary.md`.

### Error States

| Scenario | Expected Behaviour |
|---|---|
| Record has no `Last Amended` field (the normal case) | `last_amended: null` in the index. Not an error, not a gap to backfill. |
| Record has no `## Amendments` section | `amendment_count: 0`. Not an error. |
| Record has `## Amendments` rows but no `Last Amended` (e.g. the only proposal so far was rejected) | Valid combination — `amendment_count: N`, `last_amended: null`. Must not be treated as inconsistent. |
| Record has no `Supersedes` field (the normal case) | `supersedes: []`, and it contributes nothing to any other entry's `superseded_by`. |
| `Supersedes` cites an ID with no matching record | Inversion silently yields no `superseded_by` entry, mirroring today's `References` behaviour. No new validation (Question 7). |
| Record sits at `Status: Amending` when a dependent-work gate runs | Gate fails on the absence of `Approved`. No special-case handling, no distinct error message. |
| `## Errata` section present | Read by nothing, indexed by nothing. Must not appear in `index.json`. |
| Malformed `## Amendments` table (no data rows, or unparseable) | Non-fatal: count what parses, and do not fail the whole index build. Missing `Decision ID`/`Status` remain the only hard parse failures. |

## 6. Architecture Overview

### New Components

| Component | Type | Responsibility |
|---|---|---|
| `## Amendments` section | Record section (both templates) | Append-only log of proposed scoped changes and their outcomes. |
| `## Errata` section | Record section (both templates) | Append-only log of changes that provably cannot alter the decision. |
| `Last Amended` | Optional Metadata field | Signals that a record has ever been amended, and when. |
| `Supersedes` | Metadata field (both templates) | The authored side of the supersede relationship the index inverts. |
| `Amending` | Status value (Decision Records only) | Marks a record whose body contains human-unconfirmed content; blocks dependent work via the existing positive `Approved` check. |
| `last_amended`, `amendment_count` | `index.json` entry fields | Machine-readable amendment state. |
| Ladder + errata-test documentation | Skill documentation | The rung-selection table, the errata test, worked examples, and the two-commit amendment sequence. |

### Component Relationships

- The two record templates are the authoring surface; `lib/decisions.js` is the reading surface. They are coupled only through the Metadata table and section headings — which is why the `Supersedes` template field and the parse change must be specified together, and why they should land in the same wave chain.
- `skill/plan-lifecycle` owns status semantics, the commit gate, and (per Question 3) the ladder itself. `skill/decision-record` and `skill/decision-brief` own record authoring and the record templates, and point at `plan-lifecycle` for rung selection rather than restating it.
- Agent prompts and steering are consumers of the status vocabulary; neither gains new logic, only corrected wording.

### Integration Points

- `lib/decisions.js` — existing `parseMetadataTable`/`parseDecisionRecord`/`buildDecisionIndex`/`entriesEqual`/`diffDecisionIndex` pipeline; the pure/io split there must be preserved (engineering-core Rule 6).
- `lib/commands/index.js` — `aif index -d`; no interface change expected, but its staleness diff will report every entry as changed on the first run after the entry shape changes.
- `docs/decisions/index.json` — regenerated artifact, 16 entries today.
- `skills/plan-lifecycle/reference/status-vocabulary.md` and `reference/commit-gate-procedure.md` — the existing "Decision Record Tier Variants" sections are the structural precedent for Decision-Record-specific content living in a generic skill.
- `agents/architect.yaml`, `agents/engineering-manager.yaml` — the two agent prompts that reference Decision Record authoring directly.

## 7. Security Considerations

- **The errata rung is ungated by design.** Its only safeguard is the semantic test plus default-deny. The chunk that writes the agent-facing wording must reproduce both the exclusion list (`Status`, `Tier`, `Domain` are never errata) and the "doubt disqualifies" tie-breaker — an errata rung documented without its default-deny property is a governance hole, not a wording nit. Treated as an acceptance criterion, not polish.
- **No self-approval.** No chunk may introduce a path where `Status: Approved` is reached without a preceding explicit human decision. Per Question 6, Architect may *write* the field but may not *commit* it — the human's commit is what satisfies the gate, which keeps the approval artifact in a human's hands even for the amendment rung. Chunks touching `agents/architect.yaml` must not widen this beyond the single field-write permission.
- **Audit integrity.** Append-only is a security property here, not a style choice: rejected amendment rows are the only in-record evidence that a change was proposed and declined. Any chunk that edits or deletes an existing row is defective.
- **Parsing surface.** `lib/decisions.js` reads repo-local, trusted markdown, so there is no untrusted-input concern; the new section parse must still avoid catastrophic-backtracking regexes over arbitrarily long files (LOW).
- No secrets, credentials, network calls, or user data are involved in any chunk of this Epic.
