## Purpose

The single entry point every agent uses when it identifies it needs to record a decision. Applies the promotion threshold to select a Tier (A/B/C), determines Domain for Tier A/B decisions, checks the invoking agent against the domain owner, and dispatches to the skill (or convention) that actually produces the artifact.

`decision-triage` never writes a decision artifact itself. It decides *what kind* of record is needed and routes accordingly; the target skill decides *how* to produce it. Use this skill any time a decision point is identified during planning or implementation — before authoring a Decision Record, a Decision Brief, or an inline plan note.

---

## Inputs

- **Problem being decided** — the question that needs answering
- **Governing plan/chunk** — the plan or chunk in which the decision arose
- **Invoking agent's identity** — which agent is asking `decision-triage` to classify this decision

---

## Steps

### Step 1 — Gather decision context

Collect the problem being decided, the plan/chunk it arose in, and the invoking agent's identity. This context is passed through to whichever target the decision is ultimately dispatched to.

### Step 2 — Apply the promotion threshold to select Tier

Using the promotion threshold in `reference/tier-and-domain.md` (sourced from AIF-META-001's Design section):

1. Genuine trade-off between 2+ viable approaches with lasting cross-component impact → **Tier A**.
2. Else, can you name a plausible second, currently-unwritten piece of work that will need to cite this decision independently of the plan that made it? → **Tier B**.
3. Else → **Tier C**. Tier C is the default absent a genuine trade-off or a plausible independent future citation.

### Step 3 — For Tier A/B only, determine Domain

Using the Domain ownership table in `reference/tier-and-domain.md`, select the Domain that best matches the subject matter of the decision (Architecture, Process, Planning, AI-component, Quality, Testing, Meta-process). Domain determines both the ID/folder prefix and the owning agent.

If the decision doesn't clearly belong to exactly one Domain, select the closest match and flag the ambiguity — pass the flag through to the target skill so it can be noted in the eventual record's `Design`/`Impact on Planning` section. Only escalate to the human first if the ambiguity is severe enough to genuinely affect who should author the decision (global Rule 2 — ambiguity that matters gets asked, not assumed).

Tier C decisions skip this step entirely — no Domain determination applies.

### Step 4 — Check invoking agent against the domain owner

Look up the Domain's `Owner` in `reference/tier-and-domain.md`.

- If the invoking agent **matches** the domain owner, continue to Step 5.
- If the invoking agent **does not match** the domain owner, do not dispatch. Produce the hand-off signal described in `reference/handoff-signal.md` and stop. This check is a documented convention, not a tooling-enforced gate — see Edge Cases.

Tier C decisions skip this step — no domain-owner check applies.

### Step 5 — Dispatch

- **Tier A + owner match** → invoke `skill/decision-record`.
- **Tier B + owner match** → invoke `skill/decision-brief`.
- **Tier C** → no dispatch. Point the invoking agent to the Tier C inline-recording convention documented in `skill/chunk-planning` / `skill/epic-planning`.

---

## Outputs

- **Tier and Domain classification** — the selected Tier (A/B/C) and, for Tier A/B, the selected Domain, handed to the invoking agent or the dispatched target skill.
- **Dispatch** — an invocation of `skill/decision-record` (Tier A) or `skill/decision-brief` (Tier B), or a pointer to the Tier C inline-recording convention (no artifact produced by this skill in any case).
- **Hand-off signal** (only on domain-owner mismatch) — the structured payload defined in `reference/handoff-signal.md`, surfaced either to `skill/chunk-orchestration`'s Decision Hand-off Sub-Flow (orchestrated context) or directly to the human as a stop-and-report message (standalone context).

`decision-triage` never touches `{paths.decisions}/index.json` — that index is generated by `aif index -d` from the records `decision-record`/`decision-brief` produce, not by this skill.

---

## Edge Cases

- **Decision doesn't clearly belong to exactly one Domain** — select the closest match, flag the ambiguity for the target skill to note, and escalate to the human only if it's materially unclear who should author it.
- **Invoking agent doesn't match the domain owner** — stop and report via the hand-off signal (`reference/handoff-signal.md`); do not dispatch to `decision-record`/`decision-brief` on behalf of an agent outside the owning domain. This is a documented convention only — no tooling blocks an agent that ignores this step; deviations are caught in review.
- **Tier B decision later needs promotion to Tier A** — not an automatic path. Treat it as a new Tier A decision that supersedes the Tier B one via the existing `Supersedes`/`Superseded` status vocabulary (`skill/decision-record`'s concern, not this skill's).
- **Tier C decision is later cited by a second, unrelated plan** — promote it: move its content into a proper Tier B (or A) entry, assign it an ID via the target skill, and let that skill add it to the index. `decision-triage` is invoked fresh for the promotion, same as any other decision.
- **Orchestrated vs. standalone invocation** — Steps 1-5 run identically either way. The only difference is how the Step 4 hand-off signal is surfaced onward: to `skill/chunk-orchestration`'s Decision Hand-off Sub-Flow when running under orchestration, or directly to the human as a plain-text report when running standalone. See `reference/handoff-signal.md`.
- **Domain owner is not an agent that can be dispatched as a subagent within the current orchestration run** — this is the orchestrator's concern (`skill/chunk-orchestration`), not `decision-triage`'s; this skill's only obligation is producing an accurate hand-off signal.
