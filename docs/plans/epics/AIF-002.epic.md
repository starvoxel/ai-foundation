## 2. Goal

Implement AIF-META-001's Tier × Domain model for Decision Records: introduce
independent rigor tiers (A — Researched, B — Structural, C — Embedded) so ceremony
scales to decision weight; introduce per-domain ownership (Architecture, Process,
Planning, AI-component, Quality, Testing, Meta-process) so authorship routes to the
agent with standing context instead of defaulting to Architect or Tech-Lead; and
introduce a cross-domain `docs/decisions/index.json` for structural
interconnectivity. This closes the two problems AIF-META-001 documented directly
from this repo's own history: forced full-ceremony records for lightweight
decisions, and free-text/unvalidated cross-references with no discovery mechanism.
The Epic also carries out the one-time migration of the 11 existing records
(AIF-001 through AIF-011) into the new domain/ID/location scheme.

> Requirement traceability: AIF-META-001 §"Impact on Planning" — "What Tech-Lead
> must know when decomposing the Epic that implements this decision."

## 4. Feature Description

### Agent-Facing Behaviour
When an agent identifies it needs to record a decision — during planning or
implementation — it now applies a promotion threshold to pick a Tier (A/B/C)
independently of picking a Domain (subject matter). Today every decision defaults
to a single full-ceremony format authored by whichever agent happens to be doing
the work (in practice, almost always Architect or Tech-Lead by default). After this
Epic:
- Lightweight decisions no longer force full options-exploration ceremony (Tier B),
  and decisions with no lasting cross-plan relevance are recorded inline in the
  plan that made them rather than spawning a standalone file (Tier C).
- Decisions outside the current agent's own domain of standing expertise are
  authored (or at minimum reviewed/handed off) by the domain owner — e.g. a
  process/orchestration decision routes to Engineering-Manager, not Architect or
  Tech-Lead by default.
- Any agent (human or AI) can discover "what decisions exist and how they relate"
  via `docs/decisions/index.json` instead of grep-and-read across a growing flat
  folder.

### Data Flow
1. An agent identifies a decision point during planning or implementation and
   invokes `skill/decision-triage` as the entry point — it no longer applies the
   promotion threshold or determines Tier/Domain itself.
2. `decision-triage` applies the promotion threshold to select a Tier:
   - Genuine multi-option trade-off with lasting cross-component impact → Tier A.
   - A plausible second, currently-unwritten piece of work would need to cite this
     decision independently → Tier B.
   - Otherwise → Tier C (default).
3. `decision-triage` determines the Domain (Architecture, Process, Planning,
   AI-component, Quality, Testing, Meta-process) per the ownership table in
   AIF-META-001, for Tier A/B. Domain determines both the folder/ID prefix and the
   owning agent.
4. `decision-triage` dispatches:
   - Tier A → `skill/decision-record`, which writes
     `docs/decisions/{domain-folder}/{ProjectID}-{DomainCode}-{###}_{ShortTitle}.decision.md`
     using the full options-exploration skeleton, with per-domain `Design`/`Impact
     on Planning` guidance.
   - Tier B → `skill/decision-brief`, which writes the same path pattern using the
     slim skeleton.
   - Tier C → no dispatch; `decision-triage` points the agent back to the Tier C
     inline-recording convention documented in `skill/chunk-planning`/
     `skill/epic-planning`. No standalone file, no skill invocation beyond triage
     itself.
5. `decision-record`/`decision-brief` each update `docs/decisions/index.json` in
   the same commit that produces or updates a record — a required output step, not
   a separate chore. (Tier C never touches the index.)
6. Each follows `skill/plan-lifecycle`'s gate: full Draft → revision(s) → Approved
   cycle for Tier A (`decision-record`), a lighter one-shot Draft → confirm →
   Approved cycle for Tier B (`decision-brief`). Tier C rides its parent plan's own
   `plan-lifecycle` cycle — nothing separate.

### Business Rules
- Tier (rigor) and Domain (ownership) are independent axes — a Process-domain
  decision can be Tier A or Tier B; a Tier A decision is not necessarily
  Architecture-domain.
- Domain determines the authoring agent. This Epic does not mandate any specific
  hand-off mechanic (e.g. "stop and route to X") beyond what the Domain table
  already implies — see Open Question 4 for whether that needs to be made explicit
  in the skill's Steps.
- `knowledge/index.json` proactively loads only Architecture and AI-component
  domain decisions — the two domains without a single canonical implementing
  artifact that already captures the decision's effect. All other domains'
  decisions remain traceable via `docs/decisions/index.json` but are not
  proactively loaded as knowledge.
- Tier C decisions are promoted retroactively (new ID, moved into a proper Tier B
  or A entry, added to the index) if a second, unrelated plan later needs to cite
  them independently.
- No domain-owning agent receives `WebSearch`/`WebFetch` as a result of this Epic.
- Decision IDs retain the project prefix: `{ProjectID}-{DomainCode}-{###}`. Counters
  are scoped per `(project, domain)` pair.

### Error States
| Scenario | Expected Behaviour |
|---|---|
| A decision doesn't clearly belong to exactly one domain | Agent selects the closest matching domain and notes the ambiguity in the record's `Impact on Planning`/`Design` section rather than blocking. If genuinely unclear and materially affects who should author it, raise to the human per global Rule 2 (ambiguity → ask). |
| A Tier B decision later needs promotion to Tier A after the fact (unanticipated cross-component impact discovered) | Not defined by AIF-META-001 as an automatic path (only Tier C → B/A promotion is specified). Treat as a new Tier A decision that supersedes the Tier B one, using the existing `Supersedes`/`Superseded` status vocabulary. |
| `docs/decisions/index.json` is missing or malformed when a skill tries to update it | Treat as a data-integrity failure — stop, do not silently skip the index-update step, surface to the human. |
| An agent outside a domain's ownership attempts to author a Tier A/B decision in that domain | Not blocked at a tooling level by this Epic (no enforcement mechanism specified) — this is a documented convention, not a hard gate. Deviations are caught in review, same as any other steering violation. |
| A dispatched subagent (during orchestration) hits a cross-domain decision hand-off or a decision requiring approval before it can continue | `chunk-orchestration`'s Decision Hand-off Sub-Flow (Section 3) takes over: chunk is `Blocked`, Engineering-Manager authors or dispatches authorship of the decision, presents it to the human, and resumes via the existing generic unblock mechanic once `Approved`. |
| The domain owner for a decision hand-off is not an agent Engineering-Manager can dispatch as a subagent within the current orchestration run | Escalate directly to the human with the domain/tier/owner information instead of attempting a subagent dispatch — same escalation channel as any other block. |

## 5. Architecture Overview

### New Components
| Component | Type | Responsibility |
|---|---|---|
| `skills/decision-triage/` (new) | Skill | Entry point — applies the promotion threshold to pick Tier, determines Domain, dispatches to `decision-record`, `decision-brief`, or the Tier C inline convention |
| `skills/decision-record/` (modified) | Skill | Scoped explicitly to Tier A, invoked by `decision-triage`; adds Tier/Domain metadata and index-update step |
| `skills/decision-brief/` (new) | Skill | Tier B ("Structural") producer — slim skeleton, same metadata and index-update requirement, lighter gate |
| `docs/decisions/index.json` (new) | Data / registry | Cross-domain index of every Tier A/B decision — status, domain, tier, references, path |
| `docs/decisions/{domain}/` folders (new, partially existing) | Storage | Per-domain decision-record storage and ID scoping |
| `agents/engineering-manager.yaml` (modified) | Agent config | Adds Process-domain decision-authoring capability and a Hard Rule for orchestration-time decision hand-offs |
| `skills/chunk-orchestration/` (modified) | Skill | Adds Decision Hand-off Sub-Flow (Step 4) so cross-domain/approval-gated decisions raised mid-chunk are authored and resolved without derailing orchestration |

### Component Relationships
`skills/decision-triage` is the single entry point every agent uses to record a
decision; it never writes a record itself. It dispatches to `skill/decision-record`
(Tier A) or `skill/decision-brief` (Tier B), both of which produce records into
per-domain `docs/decisions/{domain}/` folders and both update
`docs/decisions/index.json` in the same commit that produces or updates a record.
`skills/plan-lifecycle` gates both Tier A and Tier B artifacts (different cycle
shape per tier) and documents that Tier C rides its parent plan's own gate.
`skills/chunk-planning` and `skills/epic-planning` document the Tier C
inline-recording convention that `decision-triage` points to directly, so
implementing/planning agents know when a decision does *not* need to leave the
plan it was made in and does not need any skill invocation beyond triage itself.
During orchestrated execution, `skill/chunk-orchestration` sits above all of this:
when a dispatched subagent invokes `decision-triage` mid-chunk and gets a Tier A/B
hand-off, Engineering-Manager (as orchestrator) is the one that actually drives
`decision-record`/`decision-brief` to completion — either by authoring directly
(Process domain) or by dispatching the owning agent — before resuming the chunk.

### Integration Points
- `skill/plan-lifecycle` — existing skill, extended (not replaced) to document the
  Tier B abbreviated gate and the Tier C non-gate.
- `skill/knowledge-authoring` — existing skill, Step 2 guidance updated for the
  domain-scoped `knowledge/index.json` consumption rule. No longer a candidate
  implementation surface for Tier B — `skill/decision-brief` is a dedicated skill
  instead (resolves Open Question 1).
- The 11 existing Decision Records — migrated in place per the table in Section 3.
- `agents/engineering-manager.yaml` — existing agent config, gains a new skill
  reference and a Process-domain decision-authoring responsibility, following the
  precedent already set for AI-Engineer's Architecture/AI-component split.
- `tests/validation/` — extended for `docs/decisions/index.json` structural
  validation (bidirectionality, path resolution) — confirmed in scope.
- `.aiconfig.json` — gains an explicit `paths.decisions: "docs/decisions"` entry —
  confirmed in scope.
- `skill/chunk-orchestration` — existing skill, gains the Decision Hand-off
  Sub-Flow so it can act on `decision-triage` hand-off signals raised by any
  dispatched subagent, not just Software-Engineer.

## 6. Security Considerations
- No new attack surface — this Epic changes documentation/process tooling and
  agent-config metadata; it introduces no new code execution paths, credential
  handling, or network-facing behavior.
- No domain-owning agent (including Engineering-Manager, which gains
  decision-authoring capability here) is granted `WebSearch`/`WebFetch` as part of
  this Epic — this is an explicit non-negotiable carried forward from
  AIF-META-001 and must be verified in the chunk that edits
  `agents/engineering-manager.yaml`.
- Migration work must preserve referential integrity of existing
  `Referenced By`/`References` fields — a broken cross-reference during migration
  is a data-integrity defect, not merely cosmetic, since `docs/decisions/index.json`
  is meant to make these relationships structurally trustworthy for the first time.
- The four "full reformat" records that are currently `Approved` (AIF-004,
  AIF-005, AIF-010, AIF-011) must genuinely go back through
  `skill/plan-lifecycle`'s human-confirmation step after reformatting — setting
  `Status: Draft` temporarily must not silently skip back to `Approved` without a
  new, real human confirmation. This is a plan-lifecycle gate, not a formality, even
  though the underlying decision content is not changing, only its format.
- The Decision Hand-off Sub-Flow must never let a chunk resume past a Tier A/B
  decision point until that decision reaches `Approved` — reusing the existing
  generic unblock mechanic (rather than inventing a shortcut) is deliberate so the
  approval gate is enforced identically here as everywhere else in
  `skill/plan-lifecycle`. A chunk must never resume on a `Deferred` decision.
