# Version numbers with many parallel PRs

## Question

How do projects assign package versions when many unrelated PRs are open, given: Node, pre-1.0, GitHub Actions, protected main (no bypass), Dependabot, a tag per merge wanted (Dependabot reads tags for the repo's own Actions), one maintainer plus AI agents?

## Pattern "version at merge, not in PR"

semantic-release and Release Drafter never put a number in the PR. The number is derived from the latest tag plus a bump level read from commits or labels. Nothing in the PR can collide. Inference: `package.json` then holds a placeholder; the real version is the tag.

## Failure modes

- Default `GITHUB_TOKEN` pushes and PRs do not trigger workflows. So required checks never run on a release PR (changesets and release-please). Fix is a PAT or GitHub App token ([release-please-action](https://github.com/googleapis/release-please-action), [community results](https://github.com/orgs/community/discussions/43460)). A bypass actor cannot be exempted from only status checks (same discussion).
- Bot commit to protected main (semantic-release/git) needs bypass or admin account ([plugin README](https://raw.githubusercontent.com/semantic-release/git/master/README.md)). Violates "no bypass".
- release-please: stale `autorelease: pending` label blocks new release PRs; needs manual relabel ([README](https://github.com/googleapis/release-please), [troubleshooting](https://github.com/googleapis/release-please/blob/main/docs/troubleshooting.md)).
- Release-PR tools batch many merges into one version: no tag per merge.
- Merge-queue interaction: not found in sources. Inference: any "latest tag + 1" job must be serialised (a concurrency group) or two merges race for one number.
- Dependabot takes the newest released tag for Actions ([GitHub blog](https://github.blog/news-insights/product-news/dependabot-now-updates-your-actions-workflows)). Whether a bare tag suffices without a Release object: unverified.

## Recommendation (inferred from the above)

Adopt semantic-release-style "assign at merge", without the file-commit plugin:

1. PR declares only the bump level (label or conventional PR title, checked in CI). No `package.json` edit in PRs.
2. A post-merge workflow on main, serialised by a concurrency group, computes next version = latest tag + level and pushes a `vX.Y.Z` tag (plus optional Release). Pre-1.0: map breaking to minor, feature and fix to patch, by workflow logic.
3. `package.json` stays a placeholder, or is stamped only in a release artifact. Nothing is pushed to main, so protection is never bypassed.
4. Unverified, test first: that the default token may push tags under the repo's tag rules, and that Dependabot picks bare tags. If tags are blocked, use a GitHub App token.

Fallback if `package.json` must hold the true version: Changesets, accepting one tag per release PR, not per merge, plus a PAT or App token for checks.
