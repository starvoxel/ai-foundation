## 2. Goal

Implement AIF-META-001's Tier × Domain model for Decision Records: introduce independent rigor tiers (A — Researched, B — Structural, C — Embedded) so ceremony scales to decision weight; introduce per-domain ownership (Architecture, Process, Planning, AI-component, Quality, Testing, Meta-process) so authorship routes to the agent with standing context instead of defaulting to Architect or Tech-Lead; and introduce a cross-domain `docs/decisions/index.json` for structural interconnectivity. This closes the two problems AIF-META-001 documented directly from this repo's own history: forced full-ceremony records for lightweight decisions, and free-text/unvalidated cross-references with no discovery mechanism.
The Epic also carries out the one-time migration of the 11 existing records (AIF-001 through AIF-011) into the new domain/ID/location scheme.

> Requirement traceability: AIF-META-001 §"Impact on Planning" — "What Tech-Lead
> must know when decomposing the Epic that implements this decision."

## 5. Feature Description

### Agent-Facing Behaviour

When an agent identifies it needs to record a decision — during planning or implementation — it now applies a promotion threshold to pick a Tier (A/B/C)
independently of picking a Domain (subject matter). Today every decision defaults to a single full-ceremony format authored by whichever agent happens to be doing the work (in practice, almost always Architect or Tech-Lead by default). After this Epic:

- Lightweight decisions no longer force full options-exploration ceremony (Tier B), and decisions with no lasting cross-plan relevance are recorded inline in the plan that made them rather than spawning a standalone file (Tier C).
- Decisions outside the current agent's own domain of standing expertise are authored (or at minimum reviewed/handed off) by the domain owner — e.g. a process/orchestration decision routes to Engineering-Manager, not Architect or Tech-Lead by default.
- Any agent (human or AI) can discover "what decisions exist and how they relate" via `docs/decisions/index.json` instead of grep-and-read across a growing flat folder, including by `tags` (rev 6). As of rev 5/6, this index is a derived artifact — the authoring agent's only job is to keep its own record's metadata table correct (including `Tags`); `aif index -d` builds the index from that.

### Data Flow

1. An agent identifies a decision point during planning or implementation and invokes `skill/decision-triage` as the entry point — it no longer applies the promotion threshold or determines Tier/Domain itself.
2. `decision-triage` applies the promotion threshold to select a Tier:
   - Genuine multi-option trade-off with lasting cross-component impact → Tier A.
   - A plausible second, currently-unwritten piece of work would need to cite this decision independently → Tier B.
   - Otherwise → Tier C (default).
3. `decision-triage` determines the Domain (Architecture, Process, Planning, AI-component, Quality, Testing, Meta-process) per the ownership table in AIF-META-001, for Tier A/B. Domain determines both the folder/ID prefix and the owning agent.
4. `decision-triage` dispatches:
   - Tier A → `skill/decision-record`, which writes `docs/decisions/{domain-folder}/{ProjectID}-{DomainCode}-{###}_{ShortTitle}.decision.md` using the full options-exploration skeleton, with per-domain `Design`/`Impact on Planning` guidance.
   - Tier B → `skill/decision-brief`, which writes the same path pattern using the slim skeleton.
   - Tier C → no dispatch; `decision-triage` points the agent back to the Tier C inline-recording convention documented in `skill/chunk-planning`/ `skill/epic-planning`. No standalone file, no skill invocation beyond triage itself.
5. **(Revised 2026-08-17, rev 6)** `docs/decisions/index.json` is derived, not hand-authored: after `decision-record`/`decision-brief` writes or updates a record's metadata table (including `Tags`), running `aif index -d` as a required step of `plan-lifecycle`'s commit-gate procedure crawls every Tier A/B record and regenerates `index.json` — including `referenced_by`/`superseded_by`, computed by inversion across the whole corpus — committed alongside the record. (Tier C never touches the index, since it has no standalone record for `aif index -d` to crawl.)
   _Original design: "`decision-record`/`decision-brief` each update `docs/decisions/index.json` in the same commit that produces or updates a record — a required output step, not a separate chore." Rev 5 replaced this with a `tests/validation/` script. Rev 6 replaces rev 5's placement with a CLI mode — see Section 4 and both Work Log entries for why._
6. Each follows `skill/plan-lifecycle`'s gate: full Draft → revision(s) → Approved cycle for Tier A (`decision-record`), a lighter one-shot Draft → confirm → Approved cycle for Tier B (`decision-brief`). Tier C rides its parent plan's own `plan-lifecycle` cycle — nothing separate.

### Business Rules

- Tier (rigor) and Domain (ownership) are independent axes — a Process-domain decision can be Tier A or Tier B; a Tier A decision is not necessarily Architecture-domain.
- Domain determines the authoring agent. This Epic does not mandate any specific hand-off mechanic (e.g. "stop and route to X") beyond what the Domain table already implies — see Open Question 4 for whether that needs to be made explicit in the skill's Steps.
- `knowledge/index.json` proactively loads only Architecture and AI-component domain decisions — the two domains without a single canonical implementing artifact that already captures the decision's effect. All other domains' decisions remain traceable via `docs/decisions/index.json` but are not proactively loaded as knowledge.
- Tier C decisions are promoted retroactively (new ID, moved into a proper Tier B or A entry, added to the index) if a second, unrelated plan later needs to cite them independently.
- No domain-owning agent receives `WebSearch`/`WebFetch` as a result of this Epic.
- Decision IDs retain the project prefix: `{ProjectID}-{DomainCode}-{###}`. Counters are scoped per `(project, domain)` pair.
- **(rev 5, unchanged in rev 6)** `docs/decisions/index.json` is a derived/generated artifact. No agent or skill hand-edits it directly — all changes to it come from running `aif index -d` against the source `.decision.md` files. This is the same trust model as any other generated artifact in the repo (e.g. `chunks.json`'s relationship to `dag-validate`, or `knowledge/index.json`'s relationship to `aif index -k`): the source of truth is the individual records; the index is a build output.
- **(New, rev 6)** `Tags` is a free-text, human/agent-authored list field on the `decision-record`/`decision-brief` metadata table, in the same spirit as `Domain`/`Tier` — there is no controlled vocabulary enforced by this Epic. If tag sprawl becomes a problem in practice, introducing a controlled vocabulary is a future concern, not decided here.

### Component Relationships

`skills/decision-triage` is the single entry point every agent uses to record a decision; it never writes a record itself. It dispatches to `skill/decision-record` (Tier A) or `skill/decision-brief` (Tier B), both of which produce records into per-domain `docs/decisions/{domain}/` folders. **(Revised, rev 5/6)** Neither skill hand-edits `docs/decisions/index.json` directly — running `aif index -d` (backed by the new `lib/decisions.js`) crawls all Tier A/B records after a record is written or updated and regenerates the index as a required step of `plan-lifecycle`'s commit-gate procedure, so the record and its index entry are always committed together without requiring the authoring skill to maintain index-graph invariants (like `referenced_by`, which no single record's author can see in full across the whole repo) by hand. This mirrors how `lib/commands/index.js`'s existing `-k` mode already relates to `knowledge/index.json` and `decision-record`/`decision-brief`/`decision-triage`'s distribution to consuming projects via the `engineering` bundle.
`skills/plan-lifecycle` gates both Tier A and Tier B artifacts (different cycle shape per tier), documents that Tier C rides its parent plan's own gate, and (rev 5/6) references `aif index -d` as a required step of the commit-gate procedure for Tier A/B records.
`skills/chunk-planning` and `skills/epic-planning` document the Tier C inline-recording convention that `decision-triage` points to directly, so implementing/planning agents know when a decision does _not_ need to leave the plan it was made in and does not need any skill invocation beyond triage itself.
During orchestrated execution, `skill/chunk-orchestration` sits above all of this:
when a dispatched subagent invokes `decision-triage` mid-chunk and gets a Tier A/B hand-off, Engineering-Manager (as orchestrator) is the one that actually drives `decision-record`/`decision-brief` to completion — either by authoring directly (Process domain) or by dispatching the owning agent — before resuming the chunk.

## 7. Security Considerations

- No new attack surface from the skill/agent/documentation portion of this Epic — those changes are documentation/process tooling and agent-config metadata; they introduce no new code execution paths, credential handling, or network-facing behavior. **(rev 6 correction)** This Epic _does_ now introduce real runtime code — the `lib/commands/index.js` generalization and new `lib/decisions.js` — governed by this project's `javascript`/`node` engineering standards (see Section 1). That code is local, deterministic, and file-system-only (reads `docs/decisions/**/*.decision.md`, writes `docs/decisions/index.json`) — no network calls, no credential handling, no new attack surface beyond what `aif index -k`/`aif snapshot` already have as shipped CLI commands with the same trust profile.
- No domain-owning agent (including Engineering-Manager, which gains decision-authoring capability here) is granted `WebSearch`/`WebFetch` as part of this Epic — this is an explicit non-negotiable carried forward from AIF-META-001 and must be verified in the chunk that edits `agents/engineering-manager.yaml`.
- Migration work must preserve referential integrity of existing `Referenced By`/`References` fields — a broken cross-reference during migration is a data-integrity defect, not merely cosmetic, since `docs/decisions/index.json` is meant to make these relationships structurally trustworthy for the first time. Since the index is now generated by crawling the migrated records, referential integrity is enforced automatically at generation time rather than depending on a human/agent correctly hand-transcribing it.
- The four "full reformat" records that are currently `Approved` (AIF-004, AIF-005, AIF-010, AIF-011) must genuinely go back through `skill/plan-lifecycle`'s human-confirmation step after reformatting — setting `Status: Draft` temporarily must not silently skip back to `Approved` without a new, real human confirmation. This is a plan-lifecycle gate, not a formality, even though the underlying decision content is not changing, only its format.
- The Decision Hand-off Sub-Flow must never let a chunk resume past a Tier A/B decision point until that decision reaches `Approved` — reusing the existing generic unblock mechanic (rather than inventing a shortcut) is deliberate so the approval gate is enforced identically here as everywhere else in `skill/plan-lifecycle`. A chunk must never resume on a `Deferred` decision.
